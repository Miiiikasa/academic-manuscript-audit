# Follow-up audit and journal revision packages

A follow-up audit compares review rounds. A journal revision audit checks
requirements for resubmission. Either can be targeted or full-package, and
both can apply to the same request.

## Follow-up audit

1. Identify the prior report and reviewed file versions, the current file
   inventory, and the scope to recheck. Reuse verified maps, issue IDs and
   evidence where still valid. Compare available dates, hashes or visible
   version markers. Do not infer version identity from a filename.
2. Check prior findings against current evidence, and inspect changed files,
   policy updates and affected cross-references for regressions. Match on
   issue ID when available and on the root cause and location when IDs
   changed. If a broader baseline item has been split, map it to the
   applicable current checks. Preserve the baseline ID in notes.
3. Internally classify items as new, changed, still open or resolved. Report
   only new, changed or still-open items in both standard outputs. A status
   change can merit reporting when it creates a new verification gap.
   Resolved items can be counted in the summary. Do not repeat unchanged
   passes or list resolved issues unless the user asks for closure details.
4. Record the prior and current versions, what was rechecked, and the limits
   of the comparison. If the earlier report or version cannot be established,
   identify the gap and report the current confirmed scope. Do not claim
   a verified change. A follow-up may find no new issues.

## Journal revision audit

Identify the revision round and applicable editor instructions in addition to
the current official journal requirements. Treat the editor or system's
documented instructions as submission-specific evidence within their scope.
Determine which revision artifacts are required, optional, or accepted as
portal fields. Confirm each artifact separately.

| Candidate artifact | What to check when applicable |
|---|---|
| Clean manuscript | Current correct version, no visible or embedded revisions or comments in the clean copy, correct review visibility and identity fields |
| Marked manuscript | Required markup or tracked changes are present, are legible and reflect the intended changes from the correct baseline |
| Response letter or portal response | Editor/reviewer points are traceable and covered, responses give accurate locations, and claimed changes agree with the current files |
| Revised supplement, figures, declarations or other files | Versions and callouts agree with the clean and marked versions and with the responses |

Use read-only comparisons of the clean manuscript and the intended final text
of the marked copy. Inspect markup and the extracted text separately. Do not
accept changes or alter files to run the comparison. Visible markup can be
required in the marked file and a defect in the clean file. Check anonymisation
under the applicable review model.

If reviewer comments, an earlier manuscript or the system response are
unavailable, record the exact coverage limit. Do not infer that every
reviewer point was addressed from the response letter alone. Apply the
[report contract](report-contract.md) states to each check. Revision-only rows
do not apply to a first submission unless the applicable instructions
explicitly request the artifact for that stage.
